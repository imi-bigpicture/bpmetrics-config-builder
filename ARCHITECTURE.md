# How it works

This app has no backend. Everything below happens in the browser: fetch schemas, parse
them, let the user select attributes, generate a config file for download.

## 1. The two source schemas

Bigpicture publishes two schemas that together define what metadata can be submitted:

| Schema | Repo | What it defines |
|---|---|---|
| **MSMdad** | [`imi-bigpicture/bigpicture-msmdad`](https://github.com/imi-bigpicture/bigpicture-msmdad) | Entities (Dataset, Biological Being, Specimen, Image, ...) and their attributes: names, descriptions, MSMdad ID numbers, and an `NA` field |
| **METAFLEX** | [`imi-bigpicture/bigpicture-metaflex`](https://github.com/imi-bigpicture/bigpicture-metaflex) | The XSD types backing those attributes — structural constraints like `minOccurs`/`use="required"` |

On load, the app fetches both live from `raw.githubusercontent.com` (`src/services/schemaFetcher.ts`,
`src/services/xsdFetcher.ts`) and caches them in `localStorage`. "Refresh Schemas" in the header
clears the cache and re-fetches. Each file resolves through a fallback chain: cache → live fetch →
stale cache → the bundled local copy in `public/msmdad/`/`public/metaflex/` → failed. The UI
reflects the outcome — a success toast only when fully live, a warning toast when any file came
from a fallback, an error only on true total failure — and `EntityList`/the attribute panel show
a real "couldn't load schemas" message instead of a blank list on total failure.

## 2. Parsing: `src/services/xmlSchemaParser.ts`

This is where the two schemas get combined into the `Entity[]` / `Attribute[]` the UI renders.
Each MSMdad attribute carries a `METAFLEX` field naming which XSD construct it corresponds to
(e.g. `StringAttributeType`, `ObjectType.Attribute`, `xs:string`) — that field is the bridge
between the two schemas.

**Required/Optional** is decided by picking whichever schema actually encodes it for that kind
of attribute, not by reconciling both:

- **Free-form attributes** (`METAFLEX` is `StringAttributeType`/`NumericAttributeType`/
  `MeasurementAttributeType`/`CodeAttributeType`/`SetAttributeType` — the generic "additional
  attributes" like sex, treatment, diagnosis): the XSD only says *some* AttributeType is allowed
  here, not which ones are mandatory. So required-ness comes from **MSMdad's own `NA` field**
  (`"not allowed"` → required, `"allowed"` → optional).
- **Everything else** (an entity's own ID, references to other entities, direct XSD-typed
  elements): the **XSD's `minOccurs`/`use`** is authoritative, looked up via
  `src/services/xsdRequirements.ts`.

Other columns, for reference:

| Column | Source |
|---|---|
| Name, Description, MSMdad ID, NA Status | MSMdad XML, read as-is |
| Type | MSMdad's `Value_Specification.Data_Type`, normalized (see note below) — **not** derived from the XSD |
| XPath | Generated by the app from the `METAFLEX` field + a hardcoded entity→XML-element table |
| XML File | Hardcoded entity→filename lookup table, not read from either schema |

**On the Type column's normalization** (`xmlSchemaParser.ts`: `normalizeDataType()`):
`Data_Type` is free text a human fills in when writing the MSMdad spec, not a controlled
vocabulary — the raw data contains three spellings of "set attribute" (`SET_ATTRIBUTE`,
`SET ATTRIBUTE`, `ATTRIBUTE SET`), five spellings of "string", and `TDB` (almost certainly a
typo for "TBD" in the spec itself). `normalizeDataType()` case-folds and collapses the actual
duplicate spellings found in the real data via a small synonym map — verified against all 200
bundled attributes, every distinct raw value is covered. Missing values or placeholder-looking
ones (`TDB`, `STATEMENT`) become `"Unknown"`, visibly different from a genuinely-asserted type,
rather than silently defaulting to `STRING`. `type` is still only used for the Type column
display and the search box's text filter — it's not part of `Selection` and never ends up in
any of the three downloaded config files (`modelJsonGenerator.ts` deliberately re-derives type
from the XPath instead of trusting this field).

## 3. Outputs

Three different downstream tools consume this app's output, so there are three generators:

- **bpmetrics config** (main Schema Explorer, Download button) — the selected attributes as
  extraction config JSON.
- **bpselect config** (`/bpselect` page, `src/pages/BpselectConfig.tsx`) — a `SelectionConfig`
  matching bpselect's `LoadConfig`. Constrained to the 7 `(entity, attribute)` filter pairs
  bpselect actually supports (`src/lib/bpselectConstants.ts`, transcribed from bpselect's own
  `selection/filter.go` — **must be kept in sync by hand** if bpselect adds pairs).
- **model.json** (`src/services/modelJsonGenerator.ts`) — SlideTap's format. Only 5 entities are
  supported (`biological_being`, `specimen`, `block`, `image`, `observations`); everything else
  is skipped with a warning toast. Attribute IDs are deterministic `UUIDv5`
  (`src/lib/uuidv5.ts`) so re-exporting the same selection always yields the same IDs.

## 4. Visualizations

`src/services/graphTraversal.ts` builds the entity relationship graph (parent/child references
between entities, e.g. Image → Slide → Block → Specimen). It backs two views: **Reference
Graph** (visual graph) and **Connection Explorer** (guided path-finding between entities, with
pre-written example questions in `src/services/suggestedPaths.ts`).

## File map

```
src/services/
  schemaFetcher.ts, xsdFetcher.ts   fetch + cache the two schemas
  xmlSchemaParser.ts                combine them into Entity[]/Attribute[] (see §2)
  xsdRequirements.ts                parse XSD minOccurs/use for required-ness
  graphTraversal.ts                 entity relationship graph
  suggestedPaths.ts                 pre-written Connection Explorer example paths
  modelJsonGenerator.ts             SlideTap model.json output
src/lib/
  bpselectConstants.ts              bpselect's supported filter pairs (hand-synced)
  modelJsonConstants.ts             SlideTap's fixed entity skeleton (hand-synced)
  uuidv5.ts                         deterministic attribute IDs for model.json
src/pages/
  Index.tsx                         main Schema Explorer page
  BpselectConfig.tsx                bpselect config page
```

## Known rough edges

- `bpselectConstants.ts` and `modelJsonConstants.ts` are manually transcribed from bpselect's
  and SlideTap's own source. If those tools change their accepted fields, this app needs a
  matching manual update — there's no automated check.
- Schema fetches are pinned to mutable branches, not tags/commits (METAFLEX → `main`, MSMdad →
  `initial`). Deliberate for now: MSMdad's `initial` branch hasn't been merged to `main` yet.
  Switch to `main` once that merge happens.
